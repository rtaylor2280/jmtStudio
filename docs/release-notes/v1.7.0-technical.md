# JMT Studio v1.7.0 — Technical Notes

Per-feature technical writeup of everything in [v1.7.0](v1.7.0.md). Each section gives the underlying problem, the approach, and the user-visible result. Audience: technical users and contributors who want to know what changed under the hood.

## Multi-bank preset organization

Prior to v1.7.0, every config had exactly one `Preset NAME[]` declaration. Users with large libraries had no way to logically group presets (e.g. "stage shows" vs "casual" vs "test builds"). The compile path also didn't distinguish between active and inactive sets — to test a subset you had to comment out the others.

v1.7.0 introduces named preset banks: multiple `Preset NAME[]` arrays in the same config, each independently selectable. CONFIGARRAY references in the BladeConfig point to the active bank. The strip UI shows banks as tabs above the preset list. Rename a bank via pencil and the rename rewrites both the `Preset[]` declaration and the matching `CONFIGARRAY(name)` call in a single atomic Monaco edit (single Ctrl+Z reverts both).

A bank-swap edge case is handled: if two banks each contain a reference to the other's name during reorder (cut/paste), the sync detects both old names still exist in the current set and skips the rewrite for that tick. Insertion of a new bank scaffolds a matching CONFIGARRAY reference; deletion surfaces orphan CONFIGARRAY references as red Monaco squigglies rather than silently breaking.

## Built-in serial monitor

JMT Studio v1.6.5 shipped without a way to talk to the board after flashing. Users had to install Arduino IDE alongside JMT Studio just to read effect probes, run `help`, or configure WS281X parameters. Switching back and forth was friction every Proffie user hit.

v1.7.0 adds a second tab to the build output panel that connects directly to the selected COM port at 115200 8N1. Switching to the serial tab auto-connects; switching away or pulling the cable releases the port cleanly. The send field echoes locally as `> cmd` and streams board response in real time. Pause buffers incoming data without losing it (cap ~150K chars).

Critical detail for Proffie users: serial is coordinated with flash. Before `electronAPI.flash` or `flashDFU` runs, the renderer calls `pauseSerialBeforeFlash()` which closes the port (avoiding Windows port-in-use). After flash completes, `resumeSerialAfterFlash()` reopens it ~800ms later if the user is still on the serial tab. No more "port in use" errors from forgotten serial connections.

Line filtering is right-click-driven: any line offers three options — "suppress lines starting with `<label>:`" (auto-detected for `Label: value` shape), "suppress lines starting with first 24 chars" (fallback), or "suppress exact line". Rules persist in user settings under `serial.suppress`. Display-time filtering only: suppressed lines get `display:none` rather than being dropped, so removing a rule un-hides them in place. Badge `funnel-icon + N` next to ⏸ pause; separate "clear filters" link appears at ≥2 filters.

Smart auto-scroll: scrolling up disengages auto-follow (with 20px tolerance so touchpad momentum doesn't kick the user out). Pending new lines show in a floating `↓ N new` pill at the bottom right. Clicking the pill, scrolling back, sending a command, clearing the log, or pressing End all re-engage auto-scroll. Count caps at `99+`.

Window focus restoration: alt-tabbing back to JMT Studio with the serial tab active focuses the send input via `setTimeout(0)` so the user can type immediately without clicking first.

## Default Config Template

`+ New` was a single-action button that always produced an empty editor. For new users, this was hostile: no starting point, no examples, no scaffolding. They'd either give up or copy/paste from somewhere else.

v1.7.0 adds a two-button choice modal on `+ New` (Blank vs Use Template). The template is a V3 scaffold with all four ProffieOS sections (`CONFIG_TOP` / `CONFIG_PROP` / `CONFIG_PRESETS` / `CONFIG_BUTTONS`) and a populated Preset + BladeConfig. The file lives at `userData/templates/default.h` and is created on first request via `template:readDefault` IPC, then read fresh each subsequent click — so any user modifications stick automatically.

Settings → Default Config Template exposes Import (file picker, replaces template) and Reset to Default (overwrites with shipped scaffold). Reset uses the inline-panel confirmation pattern (matches Clear Cache); the button is auto-disabled when current template content matches the shipped default byte-for-byte (nothing to reset).

Designed as a stepping stone toward future guided config generation — the file-based mechanism stays even when the editing UX changes.

## Link JMT Add-ons

JMT-specific style/prop headers (e.g. `jmt_fett263_wrapper.h`) need to be `#include`d in the config before they're available. New users frequently missed this step. v1.7.0 adds a one-click button that detects whether the relevant include is present and adds it if missing, placed correctly within the existing `#ifdef CONFIG_TOP` block (or scaffolds one if absent).

The detector regex matches `jmt_fett263_wrapper.h` (corrected from initial `jmt_fett_prop.h` typo — BUG-001). Conflict exclusion prevents double-including. The insertion is a single atomic Monaco edit, single Ctrl+Z removes it.

## Live board / include synchronization

The Board dropdown (V1/V2/V3) had historically been an independent UI selector. It could disagree with the `#include "proffieboard_vN_config.h"` line, which is meaningless because the compiler reads the include, not the dropdown.

v1.7.0 reverses the precedence: the `#include` line is the source of truth, and `@jmt:board` metadata is defensive fallback. Live auto-detect on edit (250ms debounce) syncs the dropdown when the include line changes. User dropdown click rewrites the include line in place as a single undoable Monaco edit, with a toast ("Board changed to X (include updated).") and ~2.7s line flash.

`event.isTrusted` guards the rewrite handler so programmatic dispatches from `loadContent` / auto-detect don't trigger phantom rewrites. When no include exists, a confirm modal asks before inserting one — placement: into existing `CONFIG_TOP` at top of block if present, else fresh `CONFIG_TOP` scaffold at top of file (after leading comments, preserved verbatim). Misspelled or malformed directives correctly fail to match — we don't guess from typos.

The "scoped, visible, reversible" triad emerged from this work as a portable no-confirm-required green-light test for user-initiated source modifications.

## Style Library enhancements

The Style Library shipped in v1.6.5 as a visual card-based library with full `StylePtr<>` support. v1.7.0 enhances it without changing the foundation.

### Charging Styles section

Style Library entries that reference `ChargeFullPropF` had coupled the user's entire library to JMT-enabled OS versions: any config without `../functions/charge_full_prop.h` failed to compile because the `using` alias referenced an undeclared symbol, even when no preset actually used the alias.

v1.7.0 adds a third section to `my_styles.h` (Charging Styles) alongside the existing Helpers and Using sections, wrapped once with `#ifdef FUNCTIONS_CHARGE_FULL_PROP_H` / `#endif`. The strip-classify-emit machinery extended with `_SL_CHARGING_HEADER`, `_SL_CHARGING_GUARD`, and `_SL_JMT_DEPENDENT_SYMBOLS` constants. `_stripStyleLibraryStructure` paired-match unwraps the `#ifdef`/`#endif`; `_classifyStyleEntries` gets `entry.isCharging`; `_applyStyleLibraryStructure` emits the third section with the wrap in helpers → charging → using order. Existing libraries auto-migrate on next save or load.

### Helper auto-wrap with inline validation

Adding a new helper silently failed when the user typed just the expression body (e.g. `Red`) instead of a full `using NAME = …;` statement. The parser couldn't locate the entry, and the helper "disappeared" from the visual view.

v1.7.0 detects missing `using` in Add mode and auto-wraps. Save handler refuses commits when name/code names don't match. `_showHelperError(msg, where)` where `where ∈ {'name','body'}` puts the red border on the right field. New `#styles-helper-monaco.invalid` CSS rule paints a red inset border on the body editor when the body is the problem. Name input runs LIVE validation as the user types (identifier rules + duplicate-name check), so the error appears immediately instead of after Save. Body editor's `onDidChangeModelContent` clears the body-invalid border as soon as the user edits.

### Atomic edits and undo for delete

`Ctrl+Z` reverted multiple actions per press because Monaco's `executeEdits` coalesces nearby edits — including across different source strings and adjacent typing — into a single undo step. Repro: click `+ Add Preset` twice, type a few chars, click `+ Add Preset` twice more → only 2 Ctrl+Z presses needed to fully revert all 5 actions.

v1.7.0 defines `_atomicEdit(monacoEditor, source, edits)` which wraps `executeEdits` with `editor.pushUndoStop()` before AND after. All 23 button-initiated `executeEdits` call sites in `renderer/index.html` converted to use it. Covers every preset operation, bank operation, board dropdown rewrite + include insert, Link Style Library, and Link JMT Add-ons.

Card delete in the visual view didn't restore on Ctrl+Z because the visual-view undo stack only captured drag-reorder snapshots. v1.7.0 snapshots the pre-delete styles content into `_styleReorderUndoStack` and clears the redo stack right before setValue, parallel to drag-reorder.

### Wrapper color resolution

Collapsed-slot color swatch reported the wrong color for any slot using a template wrapper with a class INNER parameter. Example: B2 = `StylePtr<PixelSwitchWrapper<MainHyperResponsiveRotoscopePrequelsBaseColor>>("...")` — the helper resolves to a purple style (`Rgb<118,0,194>`), but the tile displayed a white dot labeled "White".

Root cause: both color-detection sites took the OUTER name from `slot.expr` and scanned that helper's body. For a wrapper like `PixelSwitchWrapper`, the body contains color literals from the wrapper's own machinery (TransitionEffect/AlphaL boilerplate), so an early `White` won over the user-visible color which actually comes from the inner style's body.

v1.7.0 adds `_resolveLeafStyleName(expr)` that walks down through wrapper INNER class params (using existing `_getHelperTemplateParams` / `_parseCurrentTemplateArgs`) to find the leaf style name, then scans the LEAF's body for the earliest color. Both detection sites now use the leaf. Plain non-wrapper helpers are unaffected. Recursion capped at 5 levels defensively.

### Wrapper outer-color disclosure

Wrapper slots with a class INNER parameter (e.g. `StylePtr<PixelSwitchWrapper<Vader>>()`, no colorArg) displayed the inner's BASE_COLOR_ARG defaultExpr instead of the wrapper's own. On the saber this is a real two-color situation: wrapper paints its default during preon/postoff/transitions, inner paints its default during the active blade.

v1.7.0 flips merge priority so the outer wrapper's args land first; inner serves as fallback only for args the wrapper doesn't define. PixelSwitchWrapper's `Rgb<255,255,255>` now wins for BASE_COLOR_ARG. New `_detectInnerColorMismatch(slot)` detects wrapper-vs-inner color disagreement; expanded view appends an indented read-only disclosure row under Inner Style with the inner's swatch, color name, a ⚠ icon, and a one-click "Match inner" button. Collapsed-slot swatch overlays a small ⚠ at top-right when the mismatch exists, providing at-a-glance signal.

## Bracket error diagnostics

Style expressions like `StylePtr<Layers<AudioFlicker<RotateColorsX<Variation,Rgb<180,130,0>>,...>>>` can be 200+ characters long with deep nesting. A missing `>` or extra `<` mid-expression historically produced a generic compile error with no source pointer, leaving users to count brackets manually.

v1.7.0 surfaces unmatched brackets as Monaco red squigglies at the exact character with two heuristics:
- "Unmatched `>` near …Int2000>…" + "missing `<` after `Int`?" (WORD+digits before `>`)
- "Unmatched `<` near …TrFade<…" + "closing `>` missing for `TrFade`?" (last open function)

A context snippet ~44 chars around the error helps with one-liner style code. Applies to the Add Style editor (`onDidChangeModelContent`) and detail editor (`_updateDetailErrorMarkers`).

## Permissive identifier parsing with marker feedback

The previous design auto-corrected spaces in preset bank names to underscores at input time, then refused to commit anything else. This worked for the pencil-rename path but broke when users typed identifiers directly in Monaco — auto-correct would fight their typing, or invalid identifiers would silently corrupt the parser without explanation.

v1.7.0 separates the two paths:
- **Pencil = validated path**: space/hyphen auto-convert to `_`; anything else outside `[A-Za-z_][A-Za-z0-9_]*` blocks save with an inline error.
- **Monaco source = permissive**: any chars accepted (including invalid identifiers and empty names). Invalid states are flagged via red squiggle Monaco markers — no auto-correct, no toasts.

Sync runs every 50ms rebuild tick. Position-based: same-position `Preset[]` name change rewrites matching `CONFIGARRAY` refs in the same render cycle. Count change (insertion/deletion) → sync bails; orphans surface as markers.

Empty-name recovery: exactly-one empty `CONFIGARRAY()` pairs with exactly-one empty→named `Preset[]` transition. Two empty banks or two empty CONFIGARRAYs → ambiguous, no auto-fill, markers guide manual fix.

## First-run experience

A first-time user previously launched JMT Studio to a blank window with no guidance. The toolchain initialized silently in the background; if it failed, the user saw nothing useful.

v1.7.0 wires a splash on first launch with progress messages tied to toolchain init steps. Once the main window opens, the Build Output panel auto-opens with the toolchain log. Empty-state CTAs in the Config Manager guide the user to import or download a ProffieOS version. The "no version installed" banner is red and explicit about what to do next.

Toolchain init was decoupled from ProffieOS source validation: the core install (which is what takes time) runs before validating that a ProffieOS folder exists, so the first-run setup banner appears and progresses while the user installs or imports a ProffieOS version in parallel — instead of seeing only a red error first.

Three-state toolchain status replaced the previous binary ready/not-ready: error / warn / ready. The status bar's secondary indicators (port, compile, flash) hide cleanly when toolchain reports error (no OS version), keeping the bar single-line instead of wrapping.

## Dirty Save As modal

Multiple flows in v1.6.5 could lose unsaved work. Install Now → Discard fired the unsaved-changes prompt twice. The install handler only checked config-dirty, ignoring unsaved styles, version notes, helper modal, and add-style modal — those would have been silently lost on install.

v1.7.0 extracts the full guard chain into `_runQuitGuards(verb)` in `renderer/index.html`. Wired into the close handler AND Install Now. A `_updateInstallPending` flag short-circuits the close handler's guards when the install path has already run them. Net effect: a single prompt fires, covering all dirty states (config, styles, helpers, modals).

## First signed Windows installer (Microsoft Trusted Signing)

JMT Studio v1.6.5 on Windows shipped unsigned. Users saw the SmartScreen "Unknown Publisher" warning on first install. Most made it through; an unknown number bounced.

v1.7.0 signs every executable in the installer (main app, uninstaller, NSIS installer) with a Microsoft Trusted Signing certificate issued to "Ryan Taylor" after identity verification by Microsoft's third-party verifier. UAC now shows the verified publisher name. SmartScreen reputation builds faster for Trusted Signing certs than for self-purchased Authenticode because Microsoft already vouches for the identity.

Wiring: custom `build/sign.js` electron-builder hook invokes the official Microsoft `sign` CLI (`dotnet/sign`) with `code trusted-signing` subcommand, using Azure CLI credentials (`--azure-credential-type azure-cli`). Bundled third-party binaries (`arduino-cli.exe`, `dfu-util.exe`, `openocd.exe`) are explicitly skipped — we only sign our own code. Cert profile name `jmt-studio-signing` lives in the Azure Trusted Signing account at endpoint `https://wus2.codesigning.azure.net`.

## Signed + notarized Mac (both architectures)

JMT Studio v1.6.5 Mac was already signed and notarized via the existing `build/notarize.js` afterSign hook. v1.7.0 confirms the same pipeline works against today's build and adds explicit Intel cross-build via `npm run build:mac -- --x64` to produce both arm64 and x64 DMGs alongside.

Notarization uses `@electron/notarize` against Apple's notary service with `APPLE_ID` + `APPLE_APP_SPECIFIC_PASSWORD` env vars (Team ID `MJ2AAJ6PK5` hardcoded in the script). Build output reports "Notarizing..." then proceeds to DMG packaging once the ticket staples. `spctl -a -t exec -vv` reports `source=Notarized Developer ID`.

## Arch-aware in-app updater (Mac)

`main.js checkForUpdate` selects the right release asset by `process.arch`: `arm64` Macs get `-arm64.dmg`, Intel Macs get the un-suffixed `.dmg`. Independent of which arch the running app was built for — the comparison happens at update-check time.

## Non-Windows updater browser redirect

`btn-download-update` click handler at `renderer/index.html:5177-5180` short-circuits for `_updateInfo.platform !== 'win32'`: calls `openExternal('https://jedimastertech.com/jmtstudio/')` and returns. Users on Mac and Linux land on the platform-aware download page where they pick their architecture-correct file. The Windows path continues to download to `/tmp` and `shell.openPath` the installer.

## Linux dialout group banner

Linux users not in the `dialout` group can't open `/dev/ttyACM*` for flash or serial monitor, but `arduino-cli board list` (which uses libusb / sysfs, not `/dev/`) still reports the board as detected — so the failure mode was "everything looks fine until flash fails with a cryptic permission error."

v1.7.0 reads `/etc/group` to determine the dialout GID and `process.getgroups()` to check membership. When the user isn't a member, a yellow banner appears under the toolbar with the dialout-add command (`sudo usermod -aG dialout $USER`) and a Copy Commands button. Banner condition (post mid-session refinement) is system-state alone, not board presence — fires at app launch even with no board attached, so first-time Linux users see the guidance BEFORE plugging in.

## Linux udev rules banner

The Proffieboard core ships udev rules under board codenames (`49-butterfly.rules`, `49-dragonfly.rules`, `49-ladybug.rules`, `49-nucleo.rules`) — no "proffieboard" string anywhere. Without these rules in `/etc/udev/rules.d`, `dfu-util` can enumerate the DFU device via sysfs but can't open it for transfers — flash fails inside libusb with `LIBUSB_ERROR_ACCESS`.

v1.7.0 detects missing rules by scanning rules file CONTENTS for both VID `1209` AND PID `6668` in the same file. Initially the check was a substring scan for `1209` alone, but Firefox's snap ships `/etc/udev/rules.d/70-snap.firefox.rules` with `ATTRS{idVendor}=="1209"` for unrelated hardware security keys (SoloKey, Nitrokey — all in the pid.codes 1209 vendor block). On any default Ubuntu 22.04+ system with Firefox snap installed, the substring match falsely concluded rules were installed. Tightening to require `6668` (Proffieboard's PID) resolves the false positive — Firefox uses 5070, 50b0, beee, 53c0, 53c1, none of which match.

When rules are missing, a yellow banner shows the install command with `udevadm control --reload-rules && udevadm trigger` chained so users don't need to reboot — just replug the board. A reactive recovery also fires inside the flash flow: if `dfu-util` fails with `LIBUSB_ERROR_ACCESS`, the "Fix DFU Access" modal (renamed from "Fix DFU Driver" because Linux has no driver concept) presents the same command.

## Linux dfu-suffix patch

The Proffieboard core's Linux tools include a 32-bit i386 `dfu-suffix` binary at `tools/linux/dfu-suffix`. On modern Ubuntu (no `:i386` libc compat by default), the kernel can't find the 32-bit dynamic linker `/lib/ld-linux.so.2` and fork/exec returns "no such file or directory" — referring to the missing linker, not the binary. Users on a fresh Linux install hit this immediately on first compile.

v1.7.0 bundles a 64-bit `dfu-suffix` in `resources/tools/linux/` and patches it into both candidate locations on Linux: the app's isolated `arduino-data` dir AND `~/.arduino15/` (Arduino IDE default). The `--config-file` flag doesn't redirect platform discovery on Linux, so when Arduino IDE has been used previously, the system path wins even though our YAML sets `directories.data`. Patching both locations covers both layouts.

Always-overwrite (not just when missing) because the core's file exists but is broken — initial QA's "if (existsSync) skip" left the 32-bit binary in place.

## Smart port polling

JMT Studio polls for port changes every 4.5s. The cheap signal is `SerialPort.list()` (which uses libudev on Linux); only when the path set changes do we fire `ports:changed` and trigger the more expensive `getRecommendedPort` (which uses arduino-cli's libusb + sysfs).

Detection-on-unplug was prompt because the kernel detach event reaches libudev immediately. Detection-on-plug-in lagged by several poll cycles because libudev has a settle gap after USB attach — the kernel creates `/dev/ttyACM*` but libudev's published list lags by several seconds.

v1.7.0 closes the gap with a parallel signal: a cheap sysfs scan for VID `1209` in `/sys/bus/usb/devices`. The kernel populates `idVendor` the instant the device attaches, before any userspace settle. The poll signature combines both: `${paths}|${_countLinuxProffieUsb()}`. A 0→1 USB transition flips the signature even when `SerialPort.list()` hasn't updated, so `ports:changed` fires immediately on plug-in.

No-op on non-Linux: the helper early-returns at `process.platform === 'linux'`.

## Linux DFU modal relabeled

The DFU recovery modal was hardcoded "Fix DFU Driver" on every platform. Wrong on Linux: there is no driver to fix; the kernel binds cdc-acm and usbfs without any installable software — only udev rules to grant userspace access. Calling it a "driver problem" on Linux sent users searching for software that doesn't exist.

v1.7.0 platform-adapts: "Fix DFU Driver" on Windows (WinUSB really does need install), "Fix DFU Access" on Linux/Mac. Modal body, command, and status text all updated to match.

## Mac dfu-suffix patch for non-Rosetta systems

Same shape as the Linux patch but for Mac. The Proffieboard core ships an x86_64-only `dfu-suffix` at `tools/macosx/dfu-suffix`. Apple Silicon users without Rosetta installed — increasingly common on recent Macs that have never run an Intel app — hit the same cryptic fork/exec failure.

v1.7.0 bundles a universal Mach-O binary (`x86_64 + arm64`) in `resources/tools/mac/dfu-suffix` and patches it into both candidate locations: the app's isolated `arduino-data` AND `~/Library/Arduino15/`. Universal binaries dispatch the right arch slice natively at exec, so the fix works on Apple Silicon without translation and on Intel Macs without change.

## Flash metadata accuracy

JMT Studio writes `@jmt:flashed`, `@jmt:board_sn`, `@jmt:last_port` to a config's header on every successful flash. Two "different board than last flash" indicators (port and SN) compare those values to the currently detected port.

In v1.6.5 these fields appeared to update — the `@jmt:flashed` timestamp got fresh values on each flash — but `@jmt:board_sn` and `@jmt:last_port` stayed frozen at whatever the file had when first opened. The bug was invisible because users typically flash the same board repeatedly: the loaded-from-file SN matched the connected SN, no red indicator fired. The moment a user crossed a board or port boundary (Windows COM* vs Mac /dev/cu.usbmodem*, or two different physical boards), the stale fields stuck red even after successful flashes.

Root cause: the touch-reset that puts the board into DFU mode disconnects `/dev/ttyACM*` / COM*. `ports:changed` fires during the disconnect window, `refreshPorts` runs (not gated by `isDfuMode` during touch-reset flow), `clearDetectedBoard()` wipes `selectedPort` and `selectedPortSN` to null. By the time `onBuildDone` reads them to pass to `setFlashedTimestamp`, both are null. The setter's defensive guards `if (port)` / `if (sn)` then silently skipped the assignment.

v1.7.0 freezes the target port and SN at `doFlash` entry into module-scope `_flashTargetPort` / `_flashTargetSN`, and uses those in `onBuildDone` with fallback to live values. The setter's guards were also removed so null genuinely clears the field instead of silently retaining stale data — port and SN indicators short-circuit on a null lastFlashed value (no false red), so missing identity is graceful.

DFU-manual path benefits from the same setter fix: `watchForSerialAfterDfu` can grab a returning port before the kernel publishes its USB serial descriptor; now null SN writes through instead of preserving stale.

Self-heals on first successful flash after upgrade.

## Splash centering

v1.6.5 centered the splash on the parent window's bounds. On Linux, the main window's bounds during async X11 maximize aren't reliable — the splash could end up off-screen at the bottom of the display.

v1.7.0 centers on `screen.getPrimaryDisplay().workArea` instead. Correct on single-monitor. On multi-monitor it always lands on primary, which is a known limitation deferred to a future revisit (could use `screen.getDisplayNearestPoint(screen.getCursorScreenPoint())` for cursor-aware placement).

## Cache size display

Settings → Clear Compile Cache showed a size figure (e.g. "10.3 MB"). After clicking Clear, the confirmation showed a different figure (e.g. "Cleared (38.2 MB freed)"). The discrepancy was real because the display included only the compile cache directory while Clear removed the build-output directory too.

v1.7.0 reconciles the two: the displayed figure is the sum of both directories, matching what Clear actually frees.
